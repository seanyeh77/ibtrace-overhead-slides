## 第 5 張：判準：下界超過 3 % 才算有空間

收益是 1 減去改後時間除以預設時間。區間用 log 時間的 Welch t 檢定算 95 % 信賴區間。3 % 約是對照組雜訊的上限。估計值要落在實測的 0.5–1.5 倍，才算估得準。

出處：同上 §5；repo `e1/part2/ROWS.json` 的 `statistics`。

## 第 6 張：一台機器有 8 個 NUMA node

創進一號的節點開啟 SNC4，兩顆 CPU 各切成 4 個 NUMA node，每個 node 14 顆核心。網卡 mlx5_0 掛在 node 1，也就是 CPU 14–27；這一點每個 job 開跑時都會從 sysfs 檢查。其他 node 的 CPU 編號是照每個 node 連續 14 顆推的。

出處：`ROWS.json` 的 `cluster.node_check`。

## 第 30 張：分散到 8 個 node 的收益最大

天真綁核是 `srun --cpu-bind=cores`，每個 rank 綁 1 顆 CPU，落在每顆 CPU 的前 8 核。分散到 8 個 node 是 `map_ldom:0,1,2,3,4,5,6,7`。網卡側分散與遠端分散的數字接近分散到 8 個 node，見結果文件 §2。

出處：結果文件 §2。

## 第 31 張：和綁在原地比：分散更快，天真更慢

分散到 8 個 node vs 綁在原地：BT、MG、allreduce 有空間，LU、alltoall 沒有。天真綁核 vs 綁在原地：5 個都有害。偵測器 D1 修正前的建議是 `--cpu-bind=cores`。

出處：結果文件 §3 第二張表。

## 第 32 張：靠近網卡沒有影響，擠才有

網卡側分散 vs 遠端分散：每個 node 都是 4 個 rank，只差在哪一顆 CPU。分散 vs 擠到網卡旁：都在網卡那一顆 CPU，網卡側分散每個 node 4 個 rank，擠到網卡旁 node 1 有 14 個。MG 的 +1.5 % 是中位數 0.60 s vs 0.61 s。

出處：結果文件 §3、§4。

## 第 33 張：兩顆 CPU 都用，三個程式更快

這組比較同時差兩個因素（每個 node 的 rank 數與用幾顆 CPU），只當描述。可能的機制是記憶體頻寬，屬推論。

出處：結果文件 §3。

## 第 34 張：收益來自每次迭代，不是固定成本

用每一列全部的 run（短版 10 次加每種長度 5 次）擬合直線，95 % t 區間。最快的固定規則結果相同：每次迭代的差區間都大於 0，固定成本的差區間都包含 0。MG 的截距很寬，A0 自報時間的截距是負值。

出處：結果文件 §7。

## 第 35 張：執行越久，收益越大或持平

長度：BT 200、2,200 次迭代；MG 20、600 次；allreduce 200、13,000 次；alltoall 200、800 次。這是從擬合直線算的，不是各長度實測值的對比。用程式自報時間算，allreduce 的收益反而隨長度變小（+58.0 % → +27.5 %），兩種度量不一致，報告時要提。

出處：結果文件 §7 的「依長度」表。

## 第 36 張：綁核也讓執行時間穩定

CV 0 的組：BT 天真綁核；MG 天真綁核、分散到 8 個 node、遠端分散。

出處：結果文件 §4。

## 第 37 張：偵測器：一個是確認，一個全是誤報

allreduce 另外觸發 eager／rndv 邊界偵測器，但第二段沒有對應的列，只記錄。漏報：有空間卻沒有偵測器指向的比較，每個程式 2–8 個，主要是各種固定規則 vs 預設。

出處：結果文件 §5。

## 第 38 張：盲測：收益估計 4 個程式不通過

估計是 3 份開 tracer 的預設執行的中位數。allreduce 有一份是 2.43 %，來自單一 rank，中位數不受影響。

出處：結果文件 §1、§6。

## 第 40 張：初步判讀

11 月 14 日的決策樹：G1 要求估計在實測的 0.5–1.5 倍，不成立；「收益全被固定規則拿到」成立。照當時的規則，這代表工具在綁核上只剩解釋與防止有害建議的價值，下一個實驗必須加頻寬型程式，找固定規則失效的地方。這是初步判讀，尚未定案。

## 第 41 張：待討論的問題

第 1 題的選項：兩個基準都做（預設不綁、分散到 8 個 node）、只用綁好的基準、照原設計只用預設。第 3 題：可能的指標是遠端頁比例，或程式自己讀 LLC miss 的 perf 計數，後者要另外評估權限與開銷。

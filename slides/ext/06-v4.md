# 評估方式的修正

| 第三版評估的問題 | 第四版的做法 |
| --- | --- |
| 背景流量提早啟動，T 變短 | 每個狀態啟動前都等 3 s |
| 對照組偏離 0 也照樣計分 | 對照組的區間不含 0 時，先停下檢查 |
| 每次執行只有 1–2 s | 加一組 30 s 以上的執行 |

三個測試程式：LAMMPS、osu_allgather 256 KiB、NPB FT。

三個程式的對照組都通過檢查，區間都含 0 ms。

410 次執行全部成功（job 609452、609870）。

# 8 條 rail 的損失不是固定成本

| allgather 256 KiB，2 → 8 條 rail | 迭代次數 | 實測 ΔT | 第四版預測 |
| --- | ---: | ---: | ---: |
| 短執行（1.5 s） | 4,510 次 | −258.8 ms | +76.5 ms |
| 長執行（39 s） | 220,000 次 | −7,801.6 ms | +3,730 ms |

長執行慢了 T 的 22 %，固定成本只佔其中 1 %。

8 條 rail 時，每次迭代多花約 35 µs。

所有方法的校準都說 8 條比較快，方向全錯。

# 目前方法最大的盲點

| 問題 | 現況 |
| --- | --- |
| 點對點的校準 | 量不到 16 個 rank 同時做 collective 的效果 |
| 原因 | 還在查：連線數、網卡快取、PCIe 或路徑 |

所以 rail 的問題留在現在的叢集研究。
